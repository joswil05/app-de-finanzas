# T06 — Acceso, configuración inicial y bloqueo

Actualizado: 2026-10-18. Implementación y recorridos locales verificados; revisión independiente pendiente.

## Alcance implementado

- P01: correo/contraseña y Google mediante el SDK real; registro independiente por UID, confirmación de contraseña y mensajes de cancelación/red/credenciales. No hay allowlist ni identidad simulada de producción.
- Verificación: reenviar enlace, actualizar usuario y token, cerrar sesión. El perfil y las revisiones financieras solo se preparan para un usuario verificado. Los enlaces de acción se consumen una vez incluso con React Strict Mode.
- P02: solicitud neutra de recuperación, nueva contraseña y confirmación desde un enlace válido, recuperación de enlaces inválidos/vencidos.
- P03: preferencias, zona horaria, moneda del resumen, cuenta opcional con apertura mediante `buildOpening`, categorías y seguridad predeterminadas por UID. Borrador reanudable por UID. Una transacción online confirma perfil, ajustes, categorías, cuenta/apertura opcionales. IDs estables y lectura del perfil evitan duplicados al reintentar una confirmación desconocida. No se anuncia guardado local para esta transacción.
- P04/F12: PIN local de seis dígitos, PBKDF2-SHA256 con 310000 iteraciones y salt aleatorio de 16 bytes, clave por UID/dispositivo. Cinco errores obligan a esperar treinta segundos incluso al recargar. Cola local y Web Locks cuando están disponibles evitan perder intentos concurrentes. Inactividad de dos minutos desmonta la vista privada. Recuperación requiere reautenticación online y conserva el diario de pendientes.
- Cambio de sesión: `SessionOwnerGuard`, repositorio y limpieza de caché T05; coordinación entre pestañas. El cierre con pendientes permite cancelar o guardar copia y confirmar que se guardó. La vista bloqueada exige desbloquear/recuperar antes de exportar. Un fallo de limpieza bloquea el cambio de cuenta.
- Vinculación explícita: contraseña actual y Google deben autenticarse; la alternativa Google→contraseña reautentica Google antes de crear credencial. No se fusiona automáticamente por correo.
- Integración mínima: `/inicio` indica «Base financiera en construcción», perfil propio, PIN, métodos de acceso y cierre. No hay saldos ficticios. Sin configuración Firebase se presenta una pantalla honesta y una guía local navegable; `.env.local` va en la raíz.

## Adaptación de fixtures

Con aprobación del coordinador, se usó REST del emulador en lugar de añadir Admin SDK. Se restringe al proyecto `demo-finanzas-tests` y HTTP loopback `127.0.0.1:9109`; no existe fallback de producción. Se crean usuarios, se verifica por el flujo real OOB, se inicia sesión de SDK con token verificado fresco y se siembran revisiones a través de reglas Firestore en 8180 antes de navegar. A/B tienen credenciales, contextos y namespaces independientes. Referencias primarias: [Auth Emulator](https://firebase.google.com/docs/emulator-suite/connect_auth) y [Auth REST](https://firebase.google.com/docs/reference/rest/auth).
